# Database design

## Current storage

The current slice uses Node's built-in SQLite at `.data/bookable.sqlite`. Migrations `001`–`004` define identity/organizations, artist profiles/FTS, rate cards, and private shortlists/comparisons. Migration `005` stores one artist-submitted whole-day availability status per local date and IANA timezone. Migration `006` stores managed venues and events, UTC starts, local timezone, and optional ISO currency/integer minor-unit budget. Migration `007` stores booking requests, state history, and append-only quote versions. Migration `008` stores performance evidence, counterparty confirmation source, verified performance status, and one review per participant/performance. Migration `009` stores artist portfolio assets and metadata; photo bytes use the local media adapter outside the public directory and opaque IDs. Migration `010` stores email-bound invitation records with token hashes and expiry. It enforces unique email, profile name per managing organization, valid state/type values, foreign keys, and unique organization membership. Organization, artist, booking request, quote, invitation acceptance, and performance submission flows use transactions where related records change together. Sessions store SHA-256 hashes of bearer and CSRF tokens. Passwords use scrypt salt/digest records; public projections omit credentials. WAL and a busy timeout are enabled. SQLite and local media are durable local/single-node implementations, not the target scale-out infrastructure.

Artist profiles start private. Search and public detail queries require `publication_status='published'`. Category taxonomy is seeded as application-controlled classification; genres are artist-provided text. FTS is transactionally refreshed on profile edits and joined only for public discovery. A public rate card is returned only when its explicit visibility is public; private rates remain available to authorized managers. Amounts are parsed as decimal strings and converted to integer minor units with currency-specific decimal precision. Only dates explicitly marked `available` are public; unavailable notes stay manager-only. The other booking participant is recorded as the source of a verified performance. Public reputation aggregates only verified performance rows. Review eligibility is tied to a verified performance. No payment, attendance, or predictive statistic is inferred from profiles.

Shortlists and saved comparisons are private to their owning user. Only published profiles can be added to lists or comparisons. The public compare endpoint returns only published profiles and does not create a persistent organizer record. Booking and event records require membership with `organization.manage` on the relevant side; artist managers and organizers can read participant records. Quotes are versioned and immutable. Finance provider interfaces exist, but payment events have no durable database inbox/ledger yet and cannot be accepted in production.

If `.data/store.json` exists, startup imports the previous development format once. The source JSON is retained unchanged. Import is marked and repeatable. Back up both local formats before migration.

## Target relational model

For PostgreSQL, retain UUID primary keys and UTC timestamps. `users` has unique normalized email and an opaque auth-provider identifier. `organizations` has a constrained type, creator, and timestamps. `organization_members` has a unique `(organization_id,user_id)` pair, role, explicit permission grants, invitation/status fields, and audit timestamps. Foreign keys must cascade or restrict deliberately. Every private organization query must join membership and check the requested permission server-side.

PostgreSQL migration remains a deployment prerequisite. Provide an idempotent SQLite importer and preserve a backup. Avoid service-role credentials in browser code. If Supabase is selected, define RLS policies for membership isolation and test them with separate principals.

Remaining domain tables should be introduced only alongside their modules: invitations, contracts/signatures, negotiation messages, notifications, durable provider event inbox, immutable ledger/refunds/payouts, analytics snapshots, moderation/dispute cases. Money uses integer minor units plus ISO currency codes. Submitted history must retain source attribution and a distinct verification state.
